## ১. সহজ ভাষায় মূল সমস্যাটি কী?

আমরা মানুষরা খাতায় বা ক্যালকুলেটরে যেভাবে অংক লিখি, তাকে বলা হয় **Infix Notation**। এখানে অপারেটরগুলো দুটি সংখ্যার মাঝখানে বসে:
$$\text{মানুষের জন্য সহজ (Infix): } A + B$$

কিন্তু কম্পিউটার, কম্পাইলার বা ক্যালকুলেটরের হার্ডওয়্যার ব্র্যাকেটের ঝামেলা ছাড়া সহজে বুঝতে পছন্দ করে **Prefix Notation** (যার আরেক নাম *Polish Notation*, ১৯২৪ সালে ইয়ান লুকাশিভিচ আবিষ্কার করেন)। এখানে অপারেটর আগে বসে, তারপর সংখ্যা বসে:
$$\text{কম্পিউটারের জন্য সহজ (Prefix): } + A B$$

### আরেকটি উদাহরণ:
- **Infix:** `(A + B) * C`
- **Prefix:** `* + A B C`

আমাদের কাজ হলো একটি ইনফিক্স স্ট্রিংকে কোনো অতিরিক্ত স্ট্রিং মেমোরি নষ্ট না করে সরাসরি প্রিফিক্সে রূপান্তর করা।

## ২. পাঠ্যবইয়ের সনাতন পদ্ধতি বনাম আমাদের ইন-প্লেস পদ্ধতি

আপনি যদি ডেটা স্ট্রাকচারের যেকোনো সাধারণ বই খোলেন বা গুগলে সার্চ করেন, তবে দেখতে পাবেন ইনফিক্স থেকে প্রিফিক্স করার জন্য **৩টি দীর্ঘ ধাপ** শেখানো হয়:

```text
সনাতন পাঠ্যবইয়ের দীর্ঘ পদ্ধতি (৩টি পাস + অতিরিক্ত মেমোরি):
[ (A + B) * C ] 
      │
      ▼  ধাপ ১: পুরো স্ট্রিং উল্টে ফেলা (Reverse) এবং ব্র্যাকেট '(' <-> ')' অদলবদল করা
[ C * (B + A) ]
      │
      ▼  ধাপ ২: ইনফিক্স থেকে পোস্টফিক্স অ্যালগরিদম চালানো (N সাইজের নতুন অ্যারে লাগে)
[ C B A + * ]
      │
      ▼  ধাপ ৩: প্রাপ্ত ফলাফলকে আবার উল্টে ফেলা (Reverse)
[ * + A B C ]  ==> উত্তর মিলল ঠিকই, কিন্তু অতিরিক্ত মেমোরি অপচয় ও ৩ বার ট্রাভার্স করতে হলো!
```

### কেন এই সনাতন পদ্ধতি ক্ষতিকর?
1. **মেমোরির অপচয় ($O(N)$ Space):** ছোট মাইক্রোকন্ট্রোলারে (যেমন Arduino Uno-তে মাত্র ২ KB RAM) নতুন স্ট্রিং তৈরি করলেই মেমোরি ক্র্যাশ (**Out-Of-Memory**) করে।
2. **ধীরগতি ও ক্যাশ মিস:** বারবার স্ট্রিং রিভার্স করা এবং মেমোরির এপাশ-ওপাশ কপির কারণে সিপিইউ ক্যাশের কার্যক্ষমতা কমে যায়।

### আমাদের ইন-প্লেস উদ্ভাবন:
আমরা কোনো স্ট্রিং রিভার্স করব না। **আমরা সরাসরি ডান থেকে বামে স্ক্যান করব, এবং একই অ্যারের ভেতরেই ডান থেকে বামে আউটপুট লিখে ফেলব!**

```text
ইন-প্লেস সিঙ্গেল বাফার মডেল (শূন্য অতিরিক্ত স্ট্রিং মেমোরি):
ইনপুট বাফার:  [ ( A + B ) * C ]
                 ▲           ▲
                 │           │
             read_idx    write_idx (দুজনেই শেষের দিক থেকে উল্টো পথে হাঁটবে!)
```

## ৩. মূল ধারণা: "ডান-থেকে-বামে ডুয়াল রানার" মডেল

কল্পনা করুন একটি রাস্তা, যার ওপর অক্ষরগুলো লেখা আছে। দুজন ব্যক্তি রাস্তার শেষ প্রান্ত থেকে শুরু করে উল্টো দিকে (ডান থেকে বামে) হাঁটছেন:

1. **পাঠক (`read_idx`):** সে প্রতিটি অক্ষর পড়ে দেখে সেটি সংখ্যা, ব্র্যাকেট নাকি যোগ-বিয়োগের চিহ্ন।
2. **লেখক (`write_idx`):** সে সঠিক প্রিফিক্স সাজিয়ে সেই রাস্তার ওপরই আবার লিখে যায়।

```text
হাঁটার দিক: <================== (ডান থেকে বামে উল্টো পথে)

  ইনডেক্স:    0    1    2    3    4    5    6
  অ্যারে:   [ ( ][ A ][ + ][ B ][ ) ][ * ][ C ]
                                          ▲
                                          │
                                 read_idx, write_idx
```
উভয়েই শুরু করে একদম শেষের ইনডেক্স `len - 1` থেকে।

## ৪. মেমোরি সেফটির জাদুকরী নিয়ম: কেন না-পড়া ডেটা মুছে যায় না?

প্রতিটি চতুর শিক্ষার্থীর মনেই এই প্রশ্ন আসে:  
> *"যে অ্যারে থেকে অক্ষর পড়া হচ্ছে, সেই একই অ্যারেতেই যদি লেখক নতুন অক্ষর লিখতে থাকে—তাহলে কি এখনো পড়া হয়নি এমন কোনো অক্ষর মুছে যাওয়ার (Overwrite) ঝুঁকি নেই?"*

উত্তর হলো: **না, কখনোই মুছে যাবে না! এটি গাণিতিকভাবে শতভাগ নিরাপদ।**

### গাণিতিক ইনভ্যারিয়েন্ট:
$$\mathbf{read\_idx \le write\_idx} \quad \text{(প্রতিটি মাইক্রো-সেকেন্ডে)}$$

কেন `read_idx` সর্বদা `write_idx`-এর সমান বা সামনে থাকবে?
1. **সংখ্যা বা অপারেন্ড সরাসরি বসে:** যখন কোনো সংখ্যা (যেমন `C`, `B`, `A`) পাওয়া যায়, লেখক সাথে সাথে তা লিখে এবং দুজনেই এক ধাপ করে বামে সরে। ফলে তাদের দূরত্ব শূন্য থাকে।
2. **ব্র্যাকেট হারিয়ে যায়:** ইনফিক্সে ব্র্যাকেট থাকে, কিন্তু প্রিফিক্সে কোনো ব্র্যাকেট লাগে না! যখনই কোনো `)` বা `(` ব্র্যাকেট পড়া হয়, `read_idx` এক ধাপ বামে চলে যায়, কিন্তু `write_idx` কোনো কিছু না লিখে নিজের জায়গায় দাঁড়িয়ে থাকে! এর ফলে উভয়ের মাঝে একটি **নিরাপদ দূরত্ব (Safety Gap)** তৈরি হয়।
3. **অপারেটর স্ট্যাকে জমা হয়:** যখন কোনো যোগ বা গুণ চিহ্ন আসে, সেটিকে সাথে সাথে না লিখে সাময়িকভাবে একটি ছোট স্ট্যাকে জমা রাখা হয়। ফলে লেখক পেছনে পড়ে থাকে এবং পাঠক আরও এগিয়ে যায়।

যেহেতু ব্র্যাকেট বাদ যায় এবং অপারেটর স্ট্যাকে থাকে, তাই **পাঠক সর্বদা লেখকের চেয়ে কয়েক ধাপ এগিয়ে থাকে।** না-পড়া কোনো অক্ষরের ওপর কখনোই লেখক পা দিতে পারে না!

## ৫. অপারেটর স্ট্যাক: ট্রাফিক সিগন্যালের মতো সাজানো

ডান থেকে বামে হাঁটার সময় প্রিফিক্স গঠনের জন্য অপারেটরের অগ্রাধিকার (Precedence) এবং দিক (Associativity) এভাবে কাজ করে:

### অগ্রাধিকার তালিকা:
| অপারেটর | অগ্রাধিকার (Priority) | স্বাভাবিক দিক |
| :---: | :---: | :---: |
| `+`, `-` | **১** (কম) | বাম-থেকে-ডান |
| `*`, `/`, `%` | **২** (মাঝারি) | বাম-থেকে-ডান |
| `^` (পাওয়ার) | **৩** (সর্বোচ্চ) | ডান-থেকে-বাম |

### উল্টো স্ক্যানের নিয়ম:
- সাধারণ অপারেটরগুলোর (`+`, `-`, `*`, `/`) জন্য: স্ট্যাকের শীর্ষে থাকা অপারেটরের চেয়ে নতুন আসা অপারেটরের ক্ষমতা যদি **কঠোরভাবে কম** হয় (`curr < top`), তবেই স্ট্যাক থেকে বের করে লিখতে হবে।
- পাওয়ারের (`^`) জন্য: নতুন আসা পাওয়ারের ক্ষমতা যদি স্ট্যাকের শীর্ষের **সমান বা কম** হয় (`curr <= top`), তবে বের করে লিখতে হবে।
- ক্লোজিং ব্র্যাকেট `)` আসলে সরাসরি স্ট্যাকে পুশ হয়। আর ওপেনিং ব্র্যাকেট `(` আসলে যতক্ষণ না `)` পাওয়া যায়, ততক্ষণ সব অপারেটর বের করে লিখে দিতে হয়।

## ৬. ধাপে ধাপে ট্রেসিং ও ভিজ্যুয়াল টেবিল (`(A+B)*C`)

ধরি আমাদের এক্সপ্রেশন: `(A+B)*C`  
দৈর্ঘ্য $L = 7$। শুরুতে: `read_idx = 6`, `write_idx = 6`।

```text
শুরুর অবস্থা:
ইনডেক্স:     0   1   2   3   4   5   6
অ্যারে:     [ (   A   +   B   )   *   C ]
                                     ▲
                             read_idx, write_idx
স্ট্যাক: []
```

### ধাপ ১: `read_idx = 6` (অক্ষর = `'C'`)
- `'C'` একটি অপারেন্ড।
- লেখক সরাসরি লিখল: `str[write_idx--] = 'C'`। `read_idx` কমে ৫ হলো।

### ধাপ ২: `read_idx = 5` (অক্ষর = `'*'`)
- `'*'` একটি অপারেটর। স্ট্যাক ফাঁকা, তাই পুশ হলো: `['*']`।
- লেখক ৫ নম্বরেই দাঁড়িয়ে রইল, কিন্তু পাঠক চলে গেল ৪-এ (নিরাপদ দূরত্ব তৈরি হলো!)।

### ধাপ ৩: `read_idx = 4` (অক্ষর = `')'`)
- `')'` ব্র্যাকেট স্ট্যাকে পুশ হলো: `['*', ')']`। পাঠক কমে ৩ হলো।

### ধাপ ৪: `read_idx = 3` (অক্ষর = `'B'`)
- `'B'` একটি অপারেন্ড। লেখক ইনডেক্স ৫-এ লিখল `'B'`।  
*(খেয়াল করুন: ৫ নম্বরে আগে `'*'` ছিল, কিন্তু `'*'` তো আগেই আমাদের স্ট্যাকে নিরাপদ আছে! তাই কোনো ডেটা নষ্ট হয়নি)*

### ধাপ ৫: `read_idx = 2` (অক্ষর = `'+'`)
- `'+'` স্ট্যাকে গেল: `['*', ')', '+']`। পাঠক কমে ১ হলো।

### ধাপ ৬: `read_idx = 1` (অক্ষর = `'A'`)
- `'A'` লেখক ইনডেক্স ৪-এ লিখে দিল।

### ধাপ ৭: `read_idx = 0` (অক্ষর = `'('`)
- `'('` পাওয়া গেছে! ব্র্যাকেট ক্লোজ করার পালা:
  - `'+'` পপ হয়ে ইনডেক্স ৩-এ লেখা হলো।
  - `')'` পপ হয়ে বাতিল হয়ে গেল।
- পাঠক -১ হয়ে স্ক্যান শেষ করল!

### ধাপ ৮: স্ট্যাক খালি করা
- স্ট্যাকে এখনো `['*']` আছে। পপ করে ইনডেক্স ২-এ লেখা হলো। `write_idx` কমে ১ হলো।

```text
লুপ শেষের অ্যারে অবস্থা:
ইনডেক্স:     0   1   2   3   4   5   6
অ্যারে:     [ (   A   *   +   A   B   C ]
                     ▲               ▲
               write_idx+1          len-1
                     └──────┬────────┘
                      আমাদের প্রিফিক্স রেজাল্ট!
```

ইনডেক্স ২ থেকে ৬ এর দিকে তাকান: **`* + A B C`**!  
কোনো অতিরিক্ত অ্যারে ছাড়াই মূল অ্যারের ডান পাশে নিখুঁত প্রিফিক্স রূপ তৈরি হয়ে গেছে!

## ৭. লাইনের পর লাইন কোড বিশ্লেষণ (সি ল্যাঙ্গুয়েজ)

মাত্র ৪৫ লাইনের মূল সি ফাংশনটি দেখুন:

```c
void makePrefixInPlace(char str[]) {
    int len = strlen(str);
    int read_idx = len - 1;   // পয়েন্টার ১: উল্টো পথে অক্ষর পড়ার জন্য
    int write_idx = len - 1;  // পয়েন্টার ২: একই অ্যারেতে আউটপুট লেখার জন্য

    while (read_idx >= 0) {
        char current = str[read_idx];

        // ১. ক্লোজিং ব্র্যাকেট স্ট্যাকে জমা রাখা
        if (current == ')') {
            push(current);
        } 
        // ২. ওপেনিং ব্র্যাকেট আসলে জোড়া পর্যন্ত সব অপারেটর লেখা
        else if (current == '(') {
            char x;
            while ((x = pop()) != ')' && x != -1) {
                str[write_idx--] = x;
            }
        } 
        // ৩. অপারেটর আসলে অগ্রাধিকার তুলনা করে স্ট্যাক হ্যান্ডেল করা
        else if (priority(current) > 0) {
            while (top != -1 && stack[top] != ')') {
                int p_curr = priority(current);
                int p_top = priority(stack[top]);
                if (p_curr < p_top || (p_curr == p_top && isRightAssociative(current))) {
                    str[write_idx--] = pop();
                } else {
                    break;
                }
            }
            push(current);
        } 
        // ৪. সংখ্যা বা ভেরিয়েবল হলে সরাসরি অ্যারেতে লেখা
        else if (isalnum(current)) {
            str[write_idx--] = current;
        }
        
        read_idx--;
    }

    // স্ট্যাকে বাকি থাকা অপারেটরগুলোকে বের করে লেখা
    while (top != -1) {
        char x = pop();
        if (x != ')' && x != '(') {
            str[write_idx--] = x;
        }
    }

    // ৫. পেছনের প্রিফিক্স স্ট্রিংটিকে সামনে (ইনডেক্স ০-তে) টেনে আনা
    int new_len = len - 1 - write_idx;
    for (int i = 0; i < new_len; i++) {
        str[i] = str[write_idx + 1 + i];
    }
    str[new_len] = '\0'; // স্ট্রিং শেষ করার নাল ক্যারেক্টার
}
```

## ৮. চূড়ান্ত সমাপ্তি: ইনডেক্স-০ এ শিফট করা

ব্র্যাকেটগুলো বাদ পড়ার কারণে আউটপুটটি আগের চেয়ে ছোট হয়েছে:
- ইনপুট সাইজ ছিল: ৭ (`(A+B)*C`)
- আউটপুট সাইজ হয়েছে: ৫ (`*+ABC`)

ফলাফলটি বর্তমানে অ্যারের শেষভাগে (ইনডেক্স ২ থেকে ৬ এ) বসে আছে। আমরা কেবল একটি ছোট লুপ চালিয়ে পুরো রেজাল্টকে ইনডেক্স `০` থেকে বসিয়ে শেষে `\0` বসিয়ে দিই:

```text
আগে:  [ ( ][ A ][ * ][ + ][ A ][ B ][ C ]
                   ▲
             write_idx + 1

পরে:  [ * ][ + ][ A ][ B ][ C ][ \0 ]
        0    1    2    3    4     5
```
ব্যাস! একই অ্যারের ভেতর ১০০% স্ট্যান্ডার্ড নাল-টার্মিনেটেড সি স্ট্রিং তৈরি হয়ে গেল।

## ৯. শিক্ষার্থী ও বিগিনারদের সাধারণ প্রশ্ন ও উত্তর (FAQ)

### প্রশ্ন ১: স্ট্যাক কি মেমোরি নিচ্ছে না?
**উত্তর:** আমাদের ইনপুট ও আউটপুট স্ট্রিং বাফারের জন্য কোনো অতিরিক্ত মেমোরি লাগছে না ($O(1)$ Extra String Memory)। অপারেটরের জন্য যে ছোট স্ট্যাক নেওয়া হয়, তা অত্যন্ত নগণ্য। একটি সাধারণ ৩০-৪০ বাইটের ফিক্সড স্ট্যাক দিয়েই বিশ্বের যেকোনো বড় সমীকরণ সলভ করা যায়।

### প্রশ্ন ২: ব্র্যাকেটে কোনো ভুল থাকলে (যেমন `(A+B`) কোড কি ক্র্যাশ করবে?
**উত্তর:** একদমই না। কোডে বাউন্ডারি গার্ড (`top != -1`, `x != -1`) দেওয়া আছে, ফলে ব্র্যাকেট ভুল থাকলেও কোড ক্র্যাশ বা মেমোরি লিক না করে নিরাপদে রেজাল্ট বের করে দেয়।

### প্রশ্ন ৩: পাওয়ার চিহ্নে (`^`) কেন `<=` দেওয়া হয়েছে?
**উত্তর:**  
`A^B^C` সমীকরণে গণিতের নিয়মে আগে ডানের অংশের কাজ হয় ($A^{(B^C)}$)।  
আমরা যেহেতু ডান দিক থেকেই উল্টো করে আসছি, তাই ডানের পাওয়ারটি আগে বসে যায়। বামের পাওয়ারটি আসার পর তাদের অগ্রাধিকার সমান হলেও ডানের পাওয়ারকে স্ট্যাক থেকে নামিয়ে লিখতে হয়। এ কারণেই এটি `<=` শর্ত মেনে চলে।
